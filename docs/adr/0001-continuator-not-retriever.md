# 产品以「事的续接」为一等核心，兼顾无状态「话题」回溯

## Status
accepted (revised 2026-11-27)

## Context

仓库里的五份历史文档曾分别把插件定义成：可导航的地图（README）、工作区记忆检索层（proposal）、历史管理器（capability review）、索引+检索系统（spec）、四项要求的闭环（audit）。代码分布也顺着这些定义膨胀，而用户最痛的「事」这个对象一行都没有。同时，从第一性原理看，用户在 DSH 里存在两类真实场景：工作场景以「事」驱动（有没有干完、卡在哪、当前状态、下一步是什么），日常闲聊/交流场景则没有完结状态与下一步，只关心“哪个话题在哪个对话、哪一轮”。

## Decision

产品的一等核心域是「事的生命周期」（识别、状态、续接、交接）；日常闲聊不强行套状态机，归入无状态的「话题」回溯。两类场景共享「段」（会话内连续同主题轮次区间）作为中枢：对日常交流，「段」本身就是会话内话题目录（叠加现有关键词检索底座，后续再按需做跨会话同主题段聚拢）；对工作，「段」是拼成跨会话「事」的积木，且支持「话题 ↔ 事」一键互转。检索、分类、历史轨与动作全部围绕这两层组织，旧 v0 泳道图遗产先彻底清理后再建设核心域。

## Considered Options

- **纯历史检索器**：正在被平台原生搜索商品化；完美索引也救不了「想不起搜什么」和「不知下一步干啥」的人。
- **工作与闲聊割裂成双模式开关**：强迫用户在开口或翻看前先切换模式，心智负担高且与同一会话里常穿插工作和闲聊的现实冲突。
- **只做工作完全不管闲聊**：把纯交流对话强行塞进状态机只会制造大量僵尸卡片，或让用户在闲聊场景找不到“话题→对话→轮次”。

## Consequences

- 右侧抽屉升级为 `［续接］［历史］［统计］［设置］`：`续接` 为工作一等首页（仅列未收束的事），`历史` 承载关键词检索、自动分类与话题回溯，对话区右缘`历史轨`升级为「段 → 轮次」两级目录。
- 先执行 v0 遗产清理（删除未挂载的旧泳道图 UI、旧几何与三层树模块及死端点，保留 v1 底座与切段/硬证据算法零件），再独立建设「段 / 事」核心域。
- 成功判据：工作场景「打开即见、30 秒续接与精准交接」，闲聊场景「3 秒找回话题在哪个对话哪一轮」。

# 语义提炼的可靠性与可见性：绝不静默降级

## Status
accepted (2026-11-27)

## Context
真机体检发现：本机 8 个工作区中有 7 个的语义提炼 semanticUsed 为 false。根因是冷启动调用模型时漏传 sessionId，被适配器直接拒绝；而调用点用 catch 静默吞掉异常，界面上没有任何提示，用户只看到一批没有摘要、没有下一步、没有跨会话合并的垃圾卡片。

后果被量化：8 个工作区合计 237 条事中决策数为 0（一条决策都没提炼出来），78 条未收束卡片里 72 条没有下一步，跨会话合并只有 2 条。

这正是既有约束中「无静默失败」被违反的地方：**半成品被当作成品展示**，问题在无人察觉的情况下扩散到所有工作区。

## Decision
语义提炼必须**可靠且可见**：

1. **修通调用契约**：按宿主适配器要求完整传参（含 sessionId——适配器在缺失时直接拒绝），并为长输入做**分批/精简**，配套合理的超时与重试，避免会话多的工作区被超时截断。
2. **状态诚实可见**：界面必须明确区分「已深度提炼（AI 已归并并生成现状/下一步）」与「仅基础规则」，并给出**具体原因**（模型未配置 / 模型超时 / 调用失败 / 正在提炼中）与**一键重试**入口。
3. **禁止静默吞错**：任何降级都必须被记录并向用户可见；空 catch 不得用于吞掉可解释的失败。

## Considered Options
- **只修 sessionId 这一个 bug，保持静默降级**：改动最小，但下次任何原因导致失败时，用户依然会看到一个「看起来正常但其实是半成品」的界面，无法诊断。
- **提炼失败时阻塞界面直到成功**：保证质量，但把外部模型的可用性变成产品可用性的硬依赖，违背「首帧展示与核心检索不受模型影响」的既有承诺（见 [ADR-0003](0003-inferred-state-inflection-confirm-and-incremental-merge.md)）。
- **提炼失败时直接报错不给结果**：最直观，但会把「可用的规则结果」也一并丢掉，比半成品更差。

## Consequences
- 事存储需要记录提炼状态（是否用过模型、时间、失败原因），并透出到 /works 响应与客户端。
- 规则兜底路径必须**独立可用**且质量达标（见 [ADR-0009](0009-next-step-suggestion-and-resume-guidance.md)），模型只在「更好」而非「可行」的层面被依赖。
- 需要针对「模型不可用 / 超时 / 返回非法 JSON / 漏传参数」等场景的回归测试，确保状态如实上报。
